# 第二批实验：冻结计划与无人值守运行

这批实验回答四个问题：CG-ICS 的双向评分是否各自有用；单概念和完整搜索在新 query 上如何交换质量与成本；结论能否迁移到 SUIM/ISIC；预先声明的 agreement gate 能否按输入节省搜索。它沿用现有模型适配器、推理 runner、Slurm 队列和第一批环境/权重，在新的 `ics-batch2-20261116` 目录运行。第一批的完整矩阵、已完成实验及结果保留。

## 实验与解释边界

| 部分 | 对照 | 回答的问题 |
|---|---|---|
| 固定候选池评分消融 | 同一 episode、同一生成池的 combined、ref_only、query_only | 只改变排序规则时，两种评分各自贡献多少 |
| 新 query 效率 | 原 full、single_concept_full、BON=1 | 在未用于第一批结果观察的 query 上，完整搜索收益是否抵得上成本 |
| 跨域验证 | SUIM/ISIC，包含 full、single、BON=1、INSID3 和全部新控制 | 域变化后系统比较、成本和 gate 是否保持一致 |
| 提案 A | agreement gate 与原 full、staged always-search、随机 gate、初始分数 gate | 按输入选择搜索是否优于固定或随机地省搜索 |

固定候选池实验每个输入只生成一套候选池，combined 是主预测，ref_only/query_only 作为同一记录的配对 alternative masks。它们不是三次模型运行，也不是三个独立样本。候选原始打分固定 `alpha=beta=1`，三规则直接分别取乘积、reference IoU、query presence；若最大乘积低于 `1e-6`，三者共同采用相同 visual 回退。不能从测试集上选择权重。

Agreement gate 的一致性来自初始概念的 **text-only mask 与 visual-only mask**，不读取 query GT。主阈值预先固定为 `tau=0.7`；`0.5/0.9` 是敏感性分析。两个 mask 都非空且达到阈值时，接受初始概念的 joint 预测，否则继续原搜索。随机 gate 的搜索概率 `0.25/0.5/0.75` 用来展示成本前沿；它们没有事后精确匹配 agreement gate 的搜索率，因此不能写成“同预算严格控制”。`p=1` 的 staged always-search 控制额外探测的成本；`initial_score_gate` 使用预先固定的 `0.8` 初始分数阈值。

主系统比较仍是 INSID3 与 CG-ICS 完整系统比较，不能把全部差异解释成 backbone。相同 query 的多个 reference 先按 query 聚合或按 query 聚类统计，不能全部视为独立样本。新 manifest 和原图 GT 也不等于完整复现作者协议。

## 冻结工作量

13 个配置：`batch2_cgics_full`、`batch2_cgics_single`、`batch2_cgics_bon1`、`batch2_cgics_score_pool`、三个 `batch2_cgics_gate_t05/t07/t09`、三个 `batch2_cgics_random_p25/p50/p75`、`batch2_cgics_staged_search`、`batch2_cgics_score_gate`、`batch2_insid3_full`。

| scope | query 目标 | reference 目标 | 正式任务 | GPU smoke | data/preflight/collect |
|---|---:|---:|---:|---:|---:|
| core：COCO 4 folds + LVIS 10 folds | 每 fold 100，共 1,400 | 每 query 最多 3 个不同 reference | 728 | 26 | 3 |
| SUIM | 1,000 | 每 query 最多 3 个 | 156 | 13 | 3 |
| ISIC | 1,000 | 每 query 最多 3 个 | 156 | 13 | 3 |
| 合计 | 3,400 | — | **1,040** | **52** | **9** |

总计 **1,101 个队列任务**。正式 primary 记录上限为 **132,600**；这是按每个 query 都有三个有效不同 reference 算出的上限，不是实际完成数。固定候选池的两个 alternative 也不能再算成新增独立 episode。

核心 query 必须排除第一批 parent/recovery 的绑定 query：既比较图像 SHA256，也比较 COCO canonical image ID。数据收据记录请求、旧绑定、实际 query/reference 数、短缺情况、manifest/协议/资源 SHA256。任何 query 目标不足或历史证据不完整都会明确失败，不能默默降低 query 目标。

SUIM/ISIC 使用现有 Phase2 数据格式；仅缺失资源时，才走已验证来源的下载/整理。ISIC 类别必须来自作者的真实类别映射，不能凭文件名或病种顺序猜测。来源不可用、映射不足、容量不足或布局冲突会保留具体错误，仅阻止对应 scope。已有数据、环境与权重复用。core 的全量 LVIS 索引和非空检查可能需要几分钟以上；三个 scope 各自的 data/preflight CPU 时间上限为 8 小时。

## 无人值守行为和算力

一次 `start` 启动一个脱离终端的后台管理器，顺序轮询三个独立队列，并轮换 scope 优先顺序。各 scope 自动执行：

`data → preflight → 对应配置/数据集的 GPU smoke → 该配置/数据集全部正式任务 → collect/analysis`

每个 smoke 使用两个真实 episode；只有对应数据集 smoke 成功，才释放其正式任务。COCO smoke 不代替 LVIS/SUIM/ISIC 验证。独立 scope 失败不会冻结其他 scope。

共享 `highpriority` 上限和 `max_inflight` 均为 **60**，不预留槽位；实际 Slurm 队列和尚未可见的其他 scope 提交都会计入限制。CG-ICS 使用 **2 张 GPU/任务**（SAM 和 owned MLLM 各一张），INSID3 使用 **1 张 GPU/任务**。这表示尽量填满项目允许的可用提交窗口，并不表示拥有集群全部 GPU，也不保证排队时有 GPU 分配。记录实际 GPU 型号、耗时和显存；分配 GPU 秒只是计算资源代理，不能当作实际利用率或金额，也不能假定不同任务的硬件完全一样。

保留已经记录的节点排除：所有 GPU profile 排除 `A484652X3B10601`，CG-ICS MLLM 另排除 `2FS9B74`。依据是第一批修复时的 CUDA/MLLM 失败证据，不是对节点当前物理故障的断言。

每次提交前写入不可变 intent；worker 从它核对任务、冻结源码、Slurm job name/id，而不依赖尚未更新的队列 job id。独占 claim 防止重复执行覆盖结果。无法解析的 ACK 可以通过唯一作业名、Slurm 历史和 worker claim 修复；不存在证据时不会猜测成功或重复提交。PASS 仍要求 Slurm `COMPLETED/0:0` 与匹配的完成标记。

模型错误不自动重试；失败标记、日志和首次原因保留。再次 `start` 只恢复已有未结束队列，不重跑成功任务，不清空失败，不修改计划。`collect PASS` 不等于所有模型实验成功。需要补跑时，应先审计具体失败，再生成明确选择的恢复动作。

## Mac 应用与 Orion 启动

Mac 上先按交付更新包的 SHA256、备份、应用命令操作。代码修改由用户手动 commit/push；建议 commit message：

```text
Add audited batch-2 ICS scoring, transfer, and agreement-gated search experiments
```

随后在 **Orion 登录终端** 执行一次：

```bash
(
    set -e
    cd /scratch/prj0000000262_1/hansy/CE6190-Visual-Understanding
    git pull --ff-only
    export ICS_RUNTIME=/scratch/prj0000000262_1/hansy/ce6190-ics-runtime
    export SLURM_CONF=/cm/shared/apps/slurm/var/etc/slurm/slurm.conf
    export PATH=/cm/shared/apps/slurm/current/bin:$PATH
    "$ICS_RUNTIME/envs/insid3/bin/python" -I -B -u scripts/batch2_ics.py start \
        --runtime "$ICS_RUNTIME" \
        --run-dir "$ICS_RUNTIME/runs/ics-batch2-20261116"
)
```

看到 `STARTED` 只说明管理器已启动，不是 GPU smoke 已通过。之后可以退出 SSH；后台继续推进。如果相同 run 已有管理器，则返回 `ALREADY_RUNNING`，不会另开第二个。

只生成冻结计划而不启动可使用同一命令把 `start` 换成 `prepare`。第一批历史路径默认是 runtime 下 `ics-initial-20261104-spacefix` 和 `ics-recovery-20261113`；这些历史绑定用于排除旧 query，不修改第一批。

检查状态（在 Orion）：

```bash
(
    ICS_RUNTIME=/scratch/prj0000000262_1/hansy/ce6190-ics-runtime
    ICS_RUN="$ICS_RUNTIME/runs/ics-batch2-20261116"
    export SLURM_CONF=/cm/shared/apps/slurm/var/etc/slurm/slurm.conf
    export PATH=/cm/shared/apps/slurm/current/bin:$PATH
    TZ=Asia/Singapore date
    timeout -k 2s 45s "$ICS_RUNTIME/envs/insid3/bin/python" -I -B -u \
        "$ICS_RUN/source/scripts/batch2_ics.py" status --run-dir "$ICS_RUN"
    printf 'status_exit=%s\n' "$?"
    timeout -k 2s 20s squeue -r -u "$(id -un)" \
        -o '%.18i %.12P %.12T %.12M %.60j %R'
    printf 'squeue_exit=%s\n' "$?"
    tail -n 40 "$ICS_RUN/manager.log"
)
```

`status` 的 task 状态是保存的最近观察，当前命令不查询 Slurm；与实时 `squeue` 分开解释。每个 scope 在 `scopes/<scope>/rolling_state.json` 保存完整状态，`rolling_markers/`、`logs/` 和 `data/data_receipt.json` 保留证据。scope 分析在 `batch2_analysis/`；可用 `scripts/analyze_batch2.py` 的重复 `--run-dir` 合并三个 scope，只读取已存在结果。
